# RSE Plant Control and Communication Implementation

The control and communication layer developed for the RSE experimental plant was implemented as an asynchronous supervisory architecture that decouples measurement acquisition from command delivery. At the plant interface, process variables and actuator commands are exposed by an OPC UA server. A separate acquisition layer, represented in the software by a configurable OPC UA collector, can poll the registered measurement nodes concurrently, timestamp the samples, retain them in finite buffers, and synchronously publish metadata-tagged records to an InfluxDB time-series database. InfluxDB therefore acts as the historian and read-side interface for the controller, whereas the write-side interface follows a direct path from the MPC process to the OPC UA server; this separation prevents database access and control actuation from sharing the same communication path. In live operation, the MPC retrieves the supply temperature, return temperature, and volumetric flow from InfluxDB as 5-min averages, converts the flow to the units required by the prediction model, and uses a background scheduler to refresh the available plant status every 10 s and execute the optimization at a 300-s sampling period. At each control step, the controller updates its internal state, solves a 12-step receding-horizon problem, and stores measured and predicted outputs, control actions, constraint slacks, feasibility indicators, and computation times. Six commands are periodically dispatched through an independent OPC UA client: four thermal-load power setpoints and the outlet-temperature setpoints of the gas and electric boilers. Before transmission, power commands are converted from watts to kilowatts and sign-adjusted to match the plant convention, while lower admissibility thresholds are applied to power and temperature references to prevent nonphysical requests. The OPC UA writer queries the datatype of each target node and constructs a type-consistent value, thereby avoiding server-side type mismatches; communication robustness is further supported by connection-health checks, bounded data buffering, automatic reconnection, and up to five write attempts, with exceptions recorded in persistent logs. Server endpoints, database credentials, measurement registries, and actuator-node mappings are deployment-specific and supplied through environment variables or private configuration; consequently, live actuation is disabled in the public software distribution.

Communication between the supervisory controller and the experimental plant is based on a separation between data acquisition and command delivery. Measurements are collected through the OPC UA industrial protocol and made available to the MPC through an InfluxDB time-series database, which acts as a historian and read-side interface. Control actions follow an independent direct path from the MPC to the plant OPC UA server, preventing data storage operations from interfering with actuation. The asynchronous scheduling of acquisition, status updates, and optimization reflects the timing constraints of the real plant, while connection-health checks, bounded buffers, reconnection procedures, and repeated write attempts support reliable operation under transient communication failures. Deployment-specific endpoints and credentials are kept outside the public software distribution.

The control and communication architecture was designed for robust deployment of the MPC on the experimental plant. It separates data acquisition from command delivery. Measurements are acquired via the OPC UA industrial protocol and stored in an InfluxDB time-series database, from which the MPC reads them. Control actions follow an independent, direct path from the MPC to the plant OPC UA server, so that database operations cannot delay or interfere with actuation, and dispatched commands are logged separately for post-processing. The main tasks run asynchronously, each at a rate matched to the plant dynamics. The configured measurement nodes are polled every 2 s; the plant status, computed as a moving average of the measurements over a 300 s window to filter measurement noise, is updated every 10 s; and the optimization is solved and the resulting commands are dispatched with a sampling period of 900 s. The controller is deployed on a virtual machine hosted in an OpenStack environment and equipped with 8 GB of RAM and 6 vCPUs. The optimization problems are formulated in Python using CasADi and solved with IPOPT.
